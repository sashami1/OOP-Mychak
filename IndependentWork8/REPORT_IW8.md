# Звіт Самостійна робота №8

## 1. Аналіз використання у відкритих проектах (Open-Source)

1. **Dictionary<TKey, TValue> у Newtonsoft.Json**
   - **Контекст:** Використовується для кешування контрактів типів (`JsonContract`) та властивостей об'єктів для уникання повторного виклику рефлексії при серіалізації.
   - **Чому обрано:** Потрібен миттєвий пошук метаданих за типом (`System.Type`).
   - **Складність:** $O(1)$ для зчитування з кешу.
   - **Особливості:** Використовується потокобезпечна обгортка або custom equality comparer для типів.

2. **HashSet<T> у Entity Framework Core**
   - **Контекст:** Відстеження завантажених сутностей у State Manager та колекціях навігації (`ICollection<T>`).
   - **Чому обрано:** Гарантує унікальність об'єктів у контексті та дозволяє миттєво перевіряти, чи відстежується сутність.
   - **Складність:** $O(1)$ для додавання, вилучення та перевірки наявності.

3. **Комбіноване використання (Dictionary + HashSet) у AutoMapper**
   - **Контекст:** Збереження карти маппінгу типів, де ключ — джерело даних, а значення — множина підтримуваних цільових типів.
   - **Чому обрано:** Зв'язок "один до багатьох" з відсутністю дублікатів та можливістю швидкого перетину типів.
   - **Складність:** $O(1)$ доступ до ключа та $O(1)$ перевірка цільового типу.

## 2. Порівняльна таблиця складності операцій

| Операція | List<T> | Dictionary<TKey, TValue> | HashSet<T> | Коли використовувати |
| :--- | :--- | :--- | :--- | :--- |
| **Додавання** | $O(1)$ amortized | $O(1)$ amortized | $O(1)$ amortized | `List` — послідовність; `Dictionary/HashSet` — асоціативність/унікальність. |
| **Пошук за значенням** | $O(n)$ | N/A (або $O(n)$ по Values) | $O(1)$ | `HashSet` для миттєвої перевірки наявності елемента. |
| **Пошук за ключем** | N/A | $O(1)$ | N/A | `Dictionary` при наявності пар "ключ-значення". |
| **Видалення** | $O(n)$ | $O(1)$ | $O(1)$ | `HashSet/Dictionary` для частих видалень без зсуву елементів. |
| **Перевірка наявності** | $O(n)$ | $O(1)$ (по ключу) | $O(1)$ | `HashSet` значно швидший за `List.Contains()`. |

## 3. Висновки про вибір колекції

- **Dictionary кращий за List**, коли потрібен доступ до даних за унікальним ідентифікатором/ключем, а не за порядковим індексом.
- **HashSet є оптимальним**, коли головна мета — забезпечити унікальність елементів та виконувати швидкі математичні операції над множинами (`UnionWith`, `IntersectWith`, `ExceptWith`).
- **Підводні камені:** 
  - Неправильна реалізація `GetHashCode()` та `Equals()` у кастомних типах призводить до втрати елементів або витоків пам'яті.
  - Потрібно враховувати регістр рядків (використовувати `StringComparer.OrdinalIgnoreCase`).

## 4. Відповіді на контрольні запитання

1. **Переваги generic-колекцій:** Забезпечують типобезпеку на етапі компіляції та виключають витрати на упакування/розпакування (boxing/unboxing) для значущих типів.
2. **Коли що використовувати:** `Dictionary` — для пошуку значень за ключем; `HashSet` — для збереження унікального набору елементів та операцій над множинами.
3. **Вплив `IEqualityComparer<T>`:** Дозволяє налаштувати власну логіку порівняння (наприклад, без урахування регістру) та рівномірно розподілити хеш-коди для уникнення колізій.
4. **Чому інвертований індекс будують на `Dictionary<string, HashSet<int>>`:** Слово слугує унікальним ключем для пошуку $O(1)$, а `HashSet` зберігає унікальні ID документів та дозволяє швидко знаходити перетини за допомогою `IntersectWith`.
