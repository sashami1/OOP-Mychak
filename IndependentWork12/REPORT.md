# Звіт самостійної роботи 12

## 1. Порівняння LINQ та PLINQ
У тесті перевірялися числа на простоту (важка обчислювальна задача):

- **1,000,000 елементів:** LINQ ~220 ms | PLINQ ~45 ms (у 4.8 раза швидше)
- **5,000,000 елементів:** LINQ ~1100 ms | PLINQ ~210 ms (у 5.2 раза швидше)
- **10,000,000 елементів:** LINQ ~2250 ms | PLINQ ~420 ms (у 5.3 раза швидше)

**Висновок:** PLINQ чудово прискорює важкі обчислення на великих обсягах даних, бо ділить роботу між усіма ядрами процесора. Для простих або малих задач використовувати його немає сенсу — накладні витрати на створення потоків зроблять його повільнішим.

## 2. Проблема побічних ефектів (Потокобезпечність)

Якщо змінювати спільну змінну (наприклад, `sum++`) зсередини PLINQ-запиту, виникає **стан гонитви (Race Condition)**. Різні потоки перезаписують дані один одного, і підсумковий результат стає неправильним.

**Як це виправити:**
1. Використовувати безпечні атомарні операції, наприклад `Interlocked.Increment()`.
2. Взагалі уникнути побічних ефектів і використати вбудований метод PLINQ (наприклад, `.Count()`).

## 3. Головні висновки
- PLINQ варто використовувати тільки тоді, коли є великий обсяг даних та складні обчислення.
- Ніколи не змінюйте зовнішні змінні всередині PLINQ-запитів без синхронізації (`lock` або `Interlocked`).
