# Звіт з аналізу модифікації та розширення ієрархії (Самостійна робота №4)

## 1. Аналіз наслідків зміни базового класу `LibraryItem`

### Внесені зміни у похідні класи
Після додавання обов'язкового параметра `string uniqueId` до конструктора `LibraryItem` у похідних класах `Book` та `Journal` виникла помилка компіляції. Для її усунення довелося:
1. Оновити сигнатури конструкторів `Book` та `Journal`, додавши параметр `string uniqueId`.
2. Оновити виклики базових конструкторів через `: base(uniqueId, title, publicationYear)`.

### Причини необхідності змін
У C# конструктори не успадковуються автоматично. Якщо базовий клас має конструктор із параметрами (і не має конструктора за замовчуванням без параметрів), кожен похідний клас **зобов'язаний** явно викликати один із конструкторів базового класу через ключове слово `base(...)`. Зміна сигнатури базового конструктора порушує цей контракт, що й викликає помилку компіляції.

## 2. Переваги та недоліки наслідування

### Переваги
- **Повторне використання коду (Reusability):** Похідні класи успадковують логіку зберігання полів та властивостей без необхідності їх дублювання.
- **Поліморфізм:** Можливість працювати з усіма елементами бібліотеки через єдине посилання базового типу `LibraryItem` (наприклад, у списку `List<LibraryItem>`).

### Недоліки та ризики
- **Проблема «Тісно пов'язаних класів» (Tight Coupling / Fragile Base Class Problem):** Будь-яка зміна в сигнатурах методів чи конструкторів базового класу призводить до "лавинного" ламання коду в усіх його нащадках.
- **Жорсткість ієрархії:** Якщо потрібно додати нову функціональність, яка стосується лише частини класів, наслідування може змусити "забруднювати" базовий клас або створювати неприродно глибокі ієрархії.


## 3. Наслідування проти Композиції

- **Коли наслідування доцільне:** Коли між сутностями є чітке відношення **"є різновидом" (IS-A)**. Наприклад: `Book` є різновидом `LibraryItem`.
- **Коли краще використати композицію:** Коли зв'язок описується як **"має" (HAS-A)** або потрібна гнучка поведінка під час виконання. Наприклад, замість того, щоб створювати `AudioBook` через наслідування від `Book`, можна створити клас `LibraryItem`, який містить компонент `AudioTrack` чи `MediaContent`.


## 4. Відповіді на контрольні запитання

1. **Як зміна конструктора базового класу вплинула на похідні класи?**
   Додавання нового обов'язкового параметра `uniqueId` до конструктора `LibraryItem` зламало компіляцію у похідних класах `Book` та `Journal`, оскільки їхні конструктори більше не відповідали новій сигнатурі базового конструктора. Довелося оновити конструктори всіх похідних класів і передати новий параметр через `: base(...)`.

2. **Чим відрізняється розширення ієрархії через новий похідний клас від модифікації наявного базового класу?**
   Розширення через новий клас (`AudioBook`) відповідає принципу Open/Closed (система відкрита для розширення, але закрита для змін) і не порушує роботу існуючого коду. Модифікація ж базового класу потенційно зачіпає та може "зламати" всі існуючі похідні класи в ієрархії.

3. **У яких випадках для цієї задачі композиція могла б бути кращою за наслідування?**
   Композиція була б кращою, якби один об'єкт міг комбінувати кілька форматів (наприклад, сутність `LibraryItem` містить список носіїв: `PaperBook`, `AudioRecord`, `PDFFile`). Це дозволило б уникнути створення множини класів на кшталт `PaperAndAudioBook` та уникнути занадто глибоких ієрархій.

4. **Як поліморфний виклик DisplayDetails() допомагає перевірити правильність ієрархії?**
   Збереження об'єктів `Book`, `Journal` та `AudioBook` у загальний список `List<LibraryItem>` і послідовний виклик `DisplayDetails()` дозволяє переконатися, що завдяки ключовому слову `override` для кожного об'єкта виконується його власна специфічна реалізація, а не базова.
